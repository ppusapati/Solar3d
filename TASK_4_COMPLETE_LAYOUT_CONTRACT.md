# Task 4: Complete-Layout Artifact Graph Backend Contract

## Overview

This document defines the **canonical backend contract** for the `CandidateArtifactGraph` – the complete data model representing a feasible solar plant layout solution generated by ML algorithms (Tasks 4–12) and consumed by backend services (Tasks 13–25).

**Contract Status**: LOCKED (Phase 1–2)  
**Version**: 1.0  
**Date**: 2026-04-07  
**Scope**: Data model for layout generation, electrical validation, transmission routing, twin provisioning, and commissioning.

---

## 1. Contract Boundary & Purpose

### 1.1 What is CandidateArtifactGraph?

The `CandidateArtifactGraph` is a **self-contained, deterministic layout solution** containing:
- **All 6 entity types** (panels, strings, inverters, transformers, cables, fault identifiers)
- **Complete electrical topology** (who connects to whom, voltage/current at each node)
- **Routing information** (cable paths, corridor definitions)
- **Feasibility metadata** (constraint status, precision scores)
- **Full lineage** (how this candidate was generated, ranked, and selected)

### 1.2 Contract Consumers (Backend Services)

The following services **MUST** consume `CandidateArtifactGraph` without modification:

| Service | Task | Input | Output |
|---------|------|-------|--------|
| Layout Service | Task 18 | CandidateArtifactGraph | Complete layout visualization + geometry export |
| Electrical Service | Task 15 | CandidateArtifactGraph | Electrical validation report + string feasibility |
| Transmission Service | Task 20 | CandidateArtifactGraph | Transmission routing + cable BoM |
| Twin Service | Task 22 | CandidateArtifactGraph | Twin provisioning payload |
| Commissioning Service | Task 23 | CandidateArtifactGraph | Handoff artifact + asset identity mappings |

### 1.3 Contract Producers (ML Algorithms)

The following algorithms **MUST** produce valid `CandidateArtifactGraph` entities:

- Deterministic infrastructure synthesis (Task 6)
- Multi-objective optimization & Pareto generation (Tasks 7–8)
- ML ranking layer (Task 10)
- Fallback generator (always available)

## 2. Permanent Structure & Immutability

### 2.1 Artifact Graph as Immutable DAG

Once a `CandidateArtifactGraph` is created and validated (feasibility_status = "VALID"), it is **immutable**:

```
Rule 1: No entity can be modified after feasibility_status = "VALID"
Rule 2: To change a candidate, create a new artifact graph with new IDs
Rule 3: Parent-child lineage is recorded for traceability
```

**Rationale**: Immutability ensures reproducibility, audit trail integrity, and prevents accidental corruption of approved layouts.

### 2.2 Layer-Based Composition

The artifact graph is organized into **3 composition layers**:

```
Layer 1: Physical Generation
├── SolarPanel (rigid: geometry + orientation)
└── InfrastructureZone (siting anchors: roads, combiner areas)

Layer 2: Electrical Composition
├── PanelString (series-connected panels)
├── InverterGroup (strings to AC conversion)
└── TransformerNode (AC to grid voltage)

Layer 3: Routing & Protection
├── CableCorridorSegment (DC/AC paths)
└── FaultIdentifier (isolation + protection)
```

**Invariants**:
- Layer 1 entities (panels) do NOT reference Layer 2
- Layer 2 entities reference only Layer 1 IDs (panel_ids in strings)
- Layer 3 entities reference Layer 1 + 2 (cable endpoints, fault chains)
- **DAG property**: No circular dependencies

### 2.3 Entity ID Format & Uniqueness

All entity IDs are **UUID (RFC 4122)** for:
- Distributed generation (ML can run in parallel without coordination)
- Idempotent merging (same ID = same entity, no collision)
- Reproducibility (deterministic seeding with `random_seed` in MLPhaseInput)

```
Format: {prefix}-{uuid}  (optional prefix for readability)
Examples:
  panel-project1-tile1-a1f3e8a0-c3d5-...
  string-abcd1234-b2c3d4e5-...
  inverter-12345678-c1d2e3f4-...
```

## 3. Entity Contracts

### 3.1 SolarPanel Entity

**Multiplicity**: 1,000–50,000 per layout (depends on site area & density)

**Mandatory Fields** (must be populated):
- `panel_id`: UUID (Primary Key)
- `layout_id`: UUID (Foreign Key to CandidateArtifactGraph)
- `asset_id`: UUID (Foreign Key to Asset catalog)
- `geometry`: Polygon3D (4-point representation)
- `tilt_degrees`: [0, 90]
- `azimuth_degrees`: [0, 360)
- `mpp_capacity_kw`: Nameplate DC power
- `created_by`: Must be one of {"deterministic_synthesis", "ml_optimization", "user_manual"}
- `created_at`: Timestamp (audit)
- `checksum`: SHA256(geometry || tilt || azimuth) [reproducibility]

**Optional Fields**:
- `string_id`: [NULL until electrical phase] Foreign Key to PanelString
- `parent_candidate_id`: [if derived from prior candidate] UUID
- `optimization_run_id`: [if created by ML] UUID
- `shading_factor`: [if terrain analysis available] [0, 1]
- `precision_metadata`: [JSON] Generation parameters, scores, confidence

**Constraints**:
- Must pass boundary containment check (C1 from Task 3)
- Geometry must be valid Polygon (4+ vertices, CCW ordering)
- `layout_score` must be [0, 1] and non-NaN

**Feasibility States**:
- `PENDING`: Initial generation, not yet validated
- `VALID`: Passed hard constraint checks (C1–C12)
- `INVALID`: Failed constraint (reason in `feasibility_reason`)
- `UNVALIDATED`: Intentionally deferred validation

**Example**:
```go
SolarPanel{
  PanelID: "panel-solar3d-tile1-a1b2c3d4",
  LayoutID: "layout-xyz",
  AssetID: "asset-paneltype-400w",
  Geometry: Geometry{
    Vertices: []Point3D{
      {Longitude: -120.5, Latitude: 38.3, ElevationM: 500.5},
      {Longitude: -120.49, Latitude: 38.3, ElevationM: 500.7},
      {Longitude: -120.49, Latitude: 38.31, ElevationM: 500.9},
      {Longitude: -120.5, Latitude: 38.31, ElevationM: 500.8},
    },
  },
  TiltDegrees: 20.5,
  AzimuthDegrees: 180.0,
  MppCapacityKw: 0.4,
  LayoutScore: 0.92,
  CreatedBy: "deterministic_synthesis",
  Checksum: "abcd1234...",
  CreatedAt: time.Now(),
}
```

### 3.2 PanelString Entity

**Multiplicity**: 50–500 per layout

**Mandatory Fields**:
- `string_id`: UUID (Primary Key)
- `layout_id`: UUID (FK to CandidateArtifactGraph)
- `panel_ids`: []UUID (ordered series path)
- `panel_count`: int32 (length of panel_ids, must be > 0)
- `string_voltage_vdc`: Sum of panel Voc values
- `string_current_adc`: Panel Isc (current-limiting)
- `string_power_kw`: Sum of panel ratings
- `created_by`: {"deterministic_synthesis", "optimizer"}
- `created_at`: Timestamp
- `feasibility_status`: Must be one of { "PENDING", "VALID", "INVALID", "UNVALIDATED" }

**Optional Fields**:
- `network_id`: [NULL until electrical phase] FK to ElectricalNetwork
- `inverter_group_id`: [NULL until assignment] FK to InverterGroup
- `mppt_index`: [NULL until assignment] Which MPPT slot?
- `optimization_run_id`: UUID (if created by ML)
- `precision_metadata`: JSON

**Constraints** (C3–C4 from Task 3):
- Every `panel_id` in `panel_ids` must reference an existing SolarPanel
- No panel can be assigned to 2+ strings (orphan check C11)
- String voltage must fit inverter MPPT range (C3)
- Panel count must be ≤ inverter max_strings_per_mppt (C4)

**Invariant**: `panel_count == len(panel_ids)`

**Example**:
```go
PanelString{
  StringID: "string-s1-abc123",
  LayoutID: "layout-xyz",
  PanelIDs: []string{"panel-1", "panel-2", ..., "panel-24"},  // 24 panels in series
  PanelCount: 24,
  StringVoltageVdc: 600.0,  // 24 * 25V nominal
  StringCurrentAdc: 10.5,
  StringPowerKw: 9.6,  // 24 * 0.4 kW
  FeasibilityStatus: "VALID",
  CreatedBy: "deterministic_synthesis",
}
```

### 3.3 InverterGroup Entity

**Multiplicity**: 10–100 per layout

**Mandatory Fields**:
- `inverter_group_id`: UUID (Primary Key)
- `layout_id`: UUID (FK to CandidateArtifactGraph)
- `inverter_asset_id`: UUID (FK to Asset)
- `string_ids`: []UUID (list of strings fed to this inverter)
- `string_count`: int32 (len(string_ids), must be > 0)
- `position`: Point3D (inverter physical siting)
- `dc_input_kw`: Sum of string_power_kw for this inverter
- `ac_output_kw`: Inverter nameplate AC output
- `dc_ac_ratio`: dc_input_kw / ac_output_kw
- `efficiency_pct`: [0, 100]
- `created_by`: "deterministic_synthesis" | "optimizer"
- `feasibility_status`: { "PENDING", "VALID", "INVALID", "UNVALIDATED" }

**Optional Fields**:
- `network_id`: [NULL until backend] FK to ElectricalNetwork
- `position_snapped_to_feature`: "road" | "foundation" | null
- `optimization_run_id`: UUID

**Constraints** (C5–C7, C10 from Task 3):
- DC/AC ratio must be in [1.1, 1.5] (C5)
- Position must satisfy slope limit (C7)
- Position must be within max distance to road (C10)
- All strings in `string_ids` must exist
- `string_count == len(string_ids)`

**Example**:
```go
InverterGroup{
  InverterGroupID: "inverter-inv1-abc123",
  LayoutID: "layout-xyz",
  InverterAssetID: "asset-central-inv-500kw",
  StringIDs: []string{"string-s1", "string-s2", ..., "string-s30"},
  StringCount: 30,
  Position: Point3D{Longitude: -120.5, Latitude: 38.3, ElevationM: 500.0},
  DcInputKw: 240.0,  // 30 strings * 8 kW each
  AcOutputKw: 200.0,
  DcAcRatio: 1.2,
  EfficiencyPct: 98.5,
  FeasibilityStatus: "VALID",
}
```

### 3.4 TransformerNode Entity

**Multiplicity**: 1–10 per layout

**Mandatory Fields**:
- `transformer_id`: UUID (Primary Key)
- `layout_id`: UUID (FK)
- `transformer_asset_id`: UUID (FK to Asset)
- `position`: Point3D (transformer siting)
- `primary_voltage_kv`: AC voltage to grid
- `secondary_voltage_kv`: AC voltage from inverters
- `kva_rating`: Apparent power capacity
- `connected_inverter_group_ids`: []UUID
- `load_kva`: Sum of connected inverter AC outputs
- `load_utilization_pct`: (load_kva / kva_rating) * 100
- `feasibility_status`: { "PENDING", "VALID", "INVALID", "UNVALIDATED" }

**Constraints** (C6, C7, C10):
- Load ≤ rating (C6)
- Position on acceptable slope (C7)
- Position near infrastructure (C10)

**Example**:
```go
TransformerNode{
  TransformerID: "transformer-tx1-abc123",
  LayoutID: "layout-xyz",
  TransformerAssetID: "asset-250kva-transformer",
  Position: Point3D{Longitude: -120.5, Latitude: 38.3, ElevationM: 500.0},
  PrimaryVoltageKv: 34.5,    // Grid voltage
  SecondaryVoltageKv: 0.48,  // Inverter output voltage
  KvaRating: 250.0,
  ConnectedInverterGroupIDs: []string{"inverter-inv1", "inverter-inv2"},
  LoadKva: 240.0,
  LoadUtilizationPct: 96.0,
  FeasibilityStatus: "VALID",
}
```

### 3.5 CableCorridorSegment Entity

**Multiplicity**: 50–200 per layout

**Mandatory Fields**:
- `corridor_id`: UUID (Primary Key)
- `layout_id`: UUID (FK)
- `path`: LineString3D (ordered waypoints)
- `length_m`: Total cable run length
- `cable_type`: "UG_DC" | "UG_AC" | "UG_MV" | "OH_LV" | "OH_MV"
- `conductor_count`: int32 (1–4)
- `conductor_size_mm2`: Cross-sectional area
- `source_location`: SourceLocation (start point)
- `target_location`: TargetLocation (end point)
- `current_rating_adc`: Ampacity
- `voltage_drop_v`: Calculated voltage drop
- `bom_count_m`: Cable meters for BoM
- `feasibility_status`: { "PENDING", "VALID", "INVALID", "UNVALIDATED" }

**Constraints** (C8, C9):
- Ampacity ≥ peak current (C8)
- Voltage drop ≤ 3% of line voltage (C9)

**Example**:
```go
CableCorridorSegment{
  CorridorID: "cable-dc1-abc123",
  LayoutID: "layout-xyz",
  Path: LineString3D{
    Vertices: []Point3D{
      {Longitude: -120.5, Latitude: 38.3, ElevationM: 500.0},
      {Longitude: -120.5, Latitude: 38.31, ElevationM: 505.0},
      {Longitude: -120.49, Latitude: 38.31, ElevationM: 510.0},
    },
    LengthM: 2500.0,
  },
  LengthM: 2500.0,
  CableType: "UG_DC",
  ConductorCount: 2,
  ConductorSizeMm2: 35.0,
  SourceLocation: SourceLocation{LocationType: "inverter_group", EntityID: "inverter-inv1"},
  TargetLocation: TargetLocation{LocationType: "transformer", EntityID: "transformer-tx1"},
  CurrentRatingAdc: 400.0,
  VoltageDropV: 12.5,  // ~2% for 600V DC line
  BomCountM: 2500.0,
  FeasibilityStatus: "VALID",
}
```

**Multiplicity**: 20–100 per layout

**Mandatory Fields**:

## 4. Operational Contracts

### 4.1 Validation Contract (Task 4)

Every `CandidateArtifactGraph` must pass validation before entry into backend:

```go
func (g *CandidateArtifactGraph) ValidateFeasibility() error {
  // Hard constraints C1–C12 from Task 3
  // Boundary containment (requires project boundary)
  // Constraint zone avoidance (requires zone data)
  // Electrical feasibility (voltage, MPPT, capacity)
  // Topology connectivity (no orphans in Layer 3)
  // Return nil if valid, error with reason if invalid
}
```

**Enforced By**: `compute/ml-inference/artifact_graph.go` (Task 4)  
**Tested By**: Integration test suite (Task 4)

### 4.2 Reproducibility Contract

Every artifact graph must be reproducible:

```
1. Same random_seed + same MLPhaseInput → Same candidate_id + checksum
2. Entity checksum = SHA256(geometry || electrical_params || orientation)
3. Graph checksum = SHA256(all entity checksums)
4. Lineage includes optimization_run_id for attribution
```

**Verification**: `ComputeChecksum()` method must match stored checksum after deserialization.

### 4.3 Versioning Contract

```
Current Version: 1.0
  - Protobuf: ml.v1.CandidateArtifactGraph
  - Go Package: github.com/solar3d/solar3d/compute/ml-inference
  - SQL Schema: ml_artifacts.*

Breaking Changes Require:
  - Major version bump (2.0)
  - Gate A approval (Phase gate)
  - Migration script for existing candidates
  - Backwards compatibility or deprecation timeline
```

### 4.4 Serialization Contract

**Supported Formats**:

1. **Protobuf (Primary)**: ml.v1.CandidateArtifactGraph (binary + text proto formats)
2. **JSON**: Canonical JSON schema derived from proto (RFC 7159)
3. **Go Structs**: Directly serializable to/from both above

**Storage**:
- **In-Flight**: Protobuf (efficient, versioned)
- **At-Rest**: PostgreSQL (relational schema, indexed for queries)
- **Export**: JSON or GeoJSON (for visualization, integration)

### 4.5 Persistence Contract

**Primary Storage**: PostgreSQL schema `ml_artifacts.*`

**Guaranteed Properties**:
- All foreign keys enforced
- Composite indexes on (layout_id, feasibility_status, optimization_run_id)
- Geometric indexes on position/path columns (GiST for PostGIS)
- Audit timestamps (created_at, updated_at)
- Soft deletes via status enum (not physical deletion)

**Retrieval**:
```sql
-- Get all valid candidates for a project
SELECT * FROM ml_artifacts.ml_candidates
WHERE project_id = $1 AND rank <= 10
ORDER BY composite_score DESC;

-- Get artifact graph by checksum (reproducibility verification)
SELECT * FROM ml_artifacts.candidate_artifact_graphs
WHERE checksum = $1;

-- Get all panels for a layout (spatial query)
SELECT * FROM ml_artifacts.solar_panels
WHERE layout_id = $1 AND ST_Intersects(geometry_geom, $2);
```

## 5. Backend Service Integration

### 5.1 Layout Service (Task 18) – Input Contract

**What it receives**:
- `CandidateArtifactGraph` with all SolarPanel + InverterGroup geometries
- `project_id` for boundary and DEM references

**What it does**:
- Combines SolarPanel geometries into tileable grid (LayoutTile layer)
- Groups panels by string for visualization layers
- Exports as GeoJSON or CAD format
- Provides point-query API for inspection

**What it returns**: 
- LayoutTile collection with panel counts, BoM aggregates
- Geometric layers (panels, roads, equipment footprints)

**Contract**: CandidateArtifactGraph is read-only input; no modifications allowed.

---

### 5.2 Electrical Service (Task 15) – Input Contract

**What it receives**:
- `CandidateArtifactGraph` with PanelString, InverterGroup, TransformerNode entities
- Asset catalog (for electrical ratings)

**What it validates**:
- Hard constraints C3–C6 in detail (voltage, MPPT, capacity, load)
- String-level electrical assumptions (series Voc/Isc, power)
- Inverter-level assumptions (MPPT assignments, efficiency)

**What it returns**:
- ElectricalNetwork (backend entity) with feasibility report
- String viability per MPPT slot
- BoM for electrical components

**Contract**: CandidateArtifactGraph provides definitive string topology; no re-optimization.

---

### 5.3 Transmission Service (Task 20) – Input Contract

**What it receives**:
- `CandidateArtifactGraph` with CableCorridorSegment, InverterGroup, TransformerNode
- Grid interconnect point and feeder requirements

**What it validates**:
- Hard constraints C9 (voltage drop), C10 (road proximity)
- Routing alternate paths if available

**What it returns**:
- Transmission network (backend entity) with cable BoM
- Fault tree with protection coordination

**Contract**: CableCorridorSegment paths are binding; service traces endpoints.

---

### 5.4 Twin Service (Task 22) – Input Contract

**What it receives**:
- Full validated `CandidateArtifactGraph` after approval (LOD 400 pass)
- Identity mappings from commissioning phase

**What it does**:
- Creates twin state schema from artifact graph structure
- Provisions telemetry ingestion points per entity
- Sets up fault detection rules per FaultIdentifier

**What it returns**:
- Twin entity with asset identity linkages
- Telemetry schema bundle

**Contract**: Entity IDs in artifact graph = twin asset identifiers (immutable).

**Non-Breaking Changes** (may proceed):

**Breaking Changes** (require gate approval):
- Removing required fields
- Renaming existing fields
- Changing PK/FK relationships
